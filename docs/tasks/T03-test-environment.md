# T03 — отдельное задание агенту тестового окружения

Ответственный: агент тестового окружения. Ветка: `codex/t03-test-harness`. Начать только после приёмки S02 и переноса его принятого коммита в эту ветку; результат передать координатору.

## Контекст и зависимость

Выполнять после S02: в репозитории уже должен быть запускаемый Next.js/TypeScript проект. Источники требований — [`TASK.md`](../../TASK.md), архитектура — [`DESIGN.md`](../../DESIGN.md), порядок задач — [`EXECUTION_PLAN.md`](../../EXECUTION_PLAN.md). Внешняя модель и личный ключ не должны быть необходимы для разработки и воспроизведения ошибок.

Задача — подготовить **лёгкий локальный макет OpenRouter** и команды проверки, которыми потом воспользуются агенты A05, C06 и Q07. Не реализуй за них `/api/chat` и клиентский поток.

## Что сделать

1. Выбери минимальные средства проверки, совместимые с текущим проектом. Предпочти один тестовый runner и небольшой Node/TypeScript HTTP-сервер; не устанавливай полный набор инструментов ради одного сценария. Документируй необходимость каждой новой зависимости.
2. Создай локальный mock upstream, который принимает запрос совместимого формата и отдаёт `text/event-stream`. Предусмотри воспроизводимые режимы:
   - `success`: минимум три части текста с небольшой управляемой паузой и завершением `[DONE]`;
   - `rate-limit`: HTTP 429 с читаемым телом;
   - `network-failure`: недоступное соединение или явное закрытие до ответа;
   - `midstream-disconnect`: первая часть есть, затем соединение рвётся;
   - `slow`: пауза перед первым чанком, чтобы проверить Stop;
   - `timeout`: ответ молчит дольше настраиваемого тестового лимита, чтобы быстро проверить таймаут приложения;
   - `abort-observed`: на сервере видно закрытие соединения после отмены клиента.
3. Добавь тестовую конфигурацию/переменную для A05, чтобы route handler мог направлять запрос на mock upstream **только в локальном тестовом режиме**. Значение не должно задаваться из браузерного запроса и не должно позволять подменить production endpoint. Если подходящую точку подключения до A05 создать нельзя, опиши точный контракт в документации, не вставляя фиктивный route handler.
4. Добавь команды в `package.json` для автоматических проверок и запуска макета. Автоматический тест должен проверять реальное поведение макета (HTTP-статус, последовательность SSE и завершение/обрыв), а не быть пустой заглушкой. Используй стабильные свободные порты или динамический порт в тестах, чтобы не конфликтовать с dev-сервером.
5. Напиши `docs/TESTING.md`: установка, запуск приложения и макета, выбор режима, запуск тестов, ожидаемое поведение в UI после A05/C06, переключение обратно на реальный OpenRouter, ограничения. Все команды должны работать без API-ключа.
6. Проверь команды с чистым окружением без `.env.local`; сохрани фактические результаты и обнови `WORKLOG.md`.

## Технические рамки

- Формат макета следует документированному SSE OpenRouter: строки `data: ...`, пустая строка между событиями, `[DONE]` в конце успешного потока. Разделение TCP-чанков может происходить посреди строки; нельзя рассчитывать на «один чанк = одно событие».
- Макет не должен передавать реальные запросы наружу, требовать бесплатного лимита модели или записывать полный текст чата в лог.
- Для проверки отмены достаточно локально подтвердить закрытие соединения; тестовый код не должен создавать production-настройку, открывающую произвольный URL upstream.
- Не добавляй множество dummy-тестов. Позже A05 и C06 добавят проверки своих функций и интеграции.

## Артефакты и приёмка

**Артефакты:** исходник макета в `tests/` или `scripts/`, конфигурация тестов, один осмысленный автоматический тест, команды `npm test` и запуска макета, `docs/TESTING.md`, запись в `WORKLOG.md`.

**Приёмка:**

- `npm test` проходит без ключа и сети; `npm run lint` и `npm run build` остаются зелёными.
- Можно отдельно воспроизвести 200 SSE с несколькими событиями, 429, разрыв, медленный ответ и таймаут.
- Контракт подключения к `/api/chat` ясен агенту A05 без обсуждения архитектуры заново.
- Секреты и test-only endpoint не попадут в клиентский bundle или production-ответы.
- В `docs/TESTING.md` есть точные команды и ожидаемые результаты, а не только список инструментов.
