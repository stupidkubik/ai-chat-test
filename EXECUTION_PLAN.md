# План выполнения тестового задания с ИИ-агентами

Статус: подготовлен к последовательному выполнению. Источник требований — [TASK.md](TASK.md), технические решения и открытые вопросы — [DESIGN.md](DESIGN.md), исследование дизайн-навыков — [DESIGN_SKILLS.md](DESIGN_SKILLS.md). Этот план описывает порядок работы, а не заменяет эти документы.

## 1. Цель и рамки

Сделать одностраничный React-чат с бесплатной моделью OpenRouter: потоковый ответ, остановка генерации, история в рамках сессии, обработка ошибок, серверное хранение ключа, доступность с клавиатуры и мобильная версия. Опубликовать GitHub-репозиторий с PR и merge; сайт на Vercel — дополнительная демонстрация при наличии времени и подходящего аккаунта. Код должен быть понятен начинающему разработчику. Каждый существенный шаг и применение ИИ фиксируем в [WORKLOG.md](WORKLOG.md).

Работаем **по одной задаче на агента за раз, в отдельной ветке для каждого этапа**. Координатор проверяет артефакты и критерии приёмки, затем передаёт следующую задачу. Задача завершена после проверки результата, а не после сообщения агента «готово». Текущее состояние, ветку и ссылки на доказательства ведём в [docs/PROGRESS.md](docs/PROGRESS.md).

Ориентир брифа — 2–6 часов чистого времени на задание. Таймбоксы этапов ниже суммарно дают около 5 часов 45 минут; фиксируем фактическое время, а превышение и незавершённое честно описываем в README. Если время растёт, сначала упрощаем декоративные элементы, а не поток, остановку, безопасность или доступность.

## 2. Рабочие правила для каждого агента

1. Сначала прочитать `TASK.md`, `DESIGN.md`, этот план и свою карточку задачи. Проверить текущую ветку и `git status --short`; работать только в назначенной ветке и не перезаписывать чужие изменения.
2. Выполнять только свою часть и изменения, необходимые для её проверки. Не добавлять библиотеки без причины; объяснить каждую новую зависимость.
3. Оставлять простой код: короткие функции, явные состояния и типы, комментарии у неочевидных решений (например, разбор SSE и отмена потока). Не копировать большой шаблон проекта ради одной страницы.
4. Не сохранять API-ключи, токены, пользовательские сообщения или ответы в репозитории и логах. Настройки с секретами — только в окружении; в репозитории — `.env.example` без значения.
5. Проверить изменения командами из карточки. Если проверка требует ключа или внешнего сервиса, запустить локальный макет API и указать, что живой сервис ещё не проверен.
6. Передать координатору: список файлов/коммит, что сделано, результаты команд, ручные проверки, известные ограничения, принятые решения и следующий шаг. Обновить `WORKLOG.md` фактами, включая помощь ИИ и исправленные ошибки. Обновить свою строку в `docs/PROGRESS.md` до статуса «на проверке»; статус «принято» ставит и коммитит координатор в этой же ветке после проверки.
7. Агент делает осмысленный коммит в своей ветке и передаёт его на проверку. Координатор смотрит diff относительно принятого предыдущего этапа и воспроизводит проверки. Исправления остаются в той же ветке. Только после статуса «принято» следующая ветка получает результат; промежуточные ветки не сливаются в `main` и не заменяют финальный PR.

### Единый формат передачи результата

```text
Задача: <ID>
Коммит / изменённые файлы: ...
Результат: ...
Проверки: <команда или сценарий> — <результат>
Скриншоты / ссылка: ...
Решения и отклонения от DESIGN.md: ...
Ограничения / блокеры: ...
Следующий шаг: ...
```

Не писать «тесты прошли», если их не запускали. В `WORKLOG.md` указывать реальную последовательность действий и вклад агента, а не реконструировать идеальный процесс задним числом.

### Передача между ветками и финальный PR

Все девять локальных веток создаются заранее от общего документального коммита `codex/chat-app`. Поэтому перед началом каждого этапа координатор переключается на его ветку и делает fast-forward до **принятого** коммита предыдущей ветки (`git merge --ff-only <предыдущая ветка>`). После этого агент работает и коммитит только в своей ветке. Если fast-forward невозможен или в рабочем дереве есть чужие изменения, остановиться и разобрать расхождение до продолжения. Назначенная ветка и хеш принятого коммита фиксируются в `docs/PROGRESS.md`.

После приёмки R08 координатор так же обновляет `codex/p09-release`. На ней выполняются финальные проверки и, если нужны, последние исправления с повторной проверкой затронутых этапов. Затем создаётся **один обязательный финальный PR `codex/p09-release` → `main`** с описанием результата, ссылками на этапы/коммиты и фактическими проверками. PR открывается только после приёмки D01–R08; merge — после просмотра полного diff, успешных проверок и устранения замечаний. В `main` промежуточные ветки не вливаются. Пока GitHub remote не подключён, ветки существуют только локально; в P09 отправляется релизная ветка и оформляется PR.

### Решение после каждой задачи

- **Принято:** артефакты существуют, обязательные проверки воспроизведены, diff соответствует задаче, ограничения записаны.
- **На доработку:** конкретный несоответствующий критерий и способ воспроизвести проблему возвращаются агенту.
- **Блокировано:** описана внешняя зависимость и временный локальный обход. Следующая независимая задача может идти дальше, но финальный релиз не объявляется готовым.

## 4. Карточки задач

### D01 — дизайн интерфейса

Полное задание для передачи агенту: [docs/tasks/D01-design.md](docs/tasks/D01-design.md). Результат — один выбранный, воспроизводимый в CSS дизайн; состояние загрузки, остановки и ошибок описаны до начала UI-разработки. Координатор смотрит прототип в двух размерах и утверждает направление. Дизайн-система должна оставаться небольшой: несколько цветов, два уровня заголовков, единая шкала отступов.

### S02 — каркас приложения

**Передать агенту:** «Создай минимальный Next.js App Router + React + TypeScript проект по `TASK.md` и `DESIGN.md` в текущем репозитории. Сохрани существующие документы. Добавь `npm run dev`, `lint`, `build` и `.env.example` с названиями переменных без секретов. Начальная страница должна открываться и показывать заглушку будущего чата. Зафиксируй версию Node и команды запуска в README-черновике. Проверь lint/build и браузер. Не реализуй API, поток и полноценный дизайн в этой задаче».

**Артефакты:** `package.json`, lockfile, `app/`, конфигурация TS/линтера, `.env.example`, краткий README. **Приёмка:** чистая установка зависимостей воспроизводима; стартовая страница открывается; `.env.local` игнорируется Git; `npm run lint` и `npm run build` проходят. **Риск:** шаблон может добавить лишние пакеты или демонстрационный контент — убрать до передачи.

### T03 — тестовое окружение

Полное задание для передачи агенту: [docs/tasks/T03-test-environment.md](docs/tasks/T03-test-environment.md). Макет внешнего API нужен до работы с настоящим ключом. Он должен позволять воспроизвести задержку и разрыв потока, которые сложно стабильно проверить через живую модель.

### U04 — интерфейс без сети

**Передать агенту:** «По утверждённым `docs/ui/UI_SPEC.md` и прототипу сделай интерфейс чата в Next.js. В этой задаче используй тестовые данные и локальные переключаемые состояния: пустой чат, сообщение пользователя, потоковый ответ, остановлено, ошибка. Добавь семантическую разметку, видимый фокус, подписи кнопок и мобильную раскладку. Предусмотри подсказку про Enter, Shift+Enter и Esc; фактическое поведение подключит C06. Не вызывай OpenRouter и не добавляй бизнес-логику потока. Покажи снимки 1440×900 и 390×844 и отклонения от макета».

**Артефакты:** компоненты, стили, снимки/ссылка на локальный предпросмотр, запись в `WORKLOG.md`. **Приёмка:** видна иерархия сообщений; поле и отправка доступны с клавиатуры; кнопки не перекрываются на 390 px; пустое и ошибочное состояния понятны; декор не мешает чтению. Тестовые переключатели убрать или оставить только в dev-среде до релиза.

### A05 — серверный маршрут

**Передать агенту:** «Реализуй серверный `POST /api/chat` по `DESIGN.md`. Принимай только ожидаемый формат и ограниченную историю, читай `OPENROUTER_API_KEY` только на сервере, обращайся к актуальному бесплатному model ID OpenRouter, транслируй поток без буферизации и возвращай понятные статусы для отсутствующего ключа, 400, 429, таймаута, ошибок upstream и недоступности сети. Подключи макет из T03 для локальной проверки. Не добавляй БД, auth и client-side секреты. Документируй только нетривиальные части».

**Артефакты:** route handler, небольшие функции нормализации/валидации, тесты для значимых веток, описание переменных. **Приёмка:** запрос к макету без ключа работает только при серверном переключателе в dev/test; production не может обратиться к макету или работать без ключа; плохой ввод отвергается до OpenRouter; ключ отсутствует в клиентском bundle и ответах; 429, таймаут и обрыв не превращаются в ложный успешный ответ; отмена входящего запроса закрывает запрос к upstream. A05 реализует таймаут upstream, включая ошибку внутри начатого SSE, и включает поддержку отмены для Node.js функции Vercel. Перед реализацией проверить текущие официальные требования OpenRouter к streaming и доступности выбранной модели; живой запрос выполнить после получения ключа.

### C06 — клиентский поток и остановка

**Передать агенту:** «Соедини готовый UI с `/api/chat`. Отправка добавляет сообщение пользователя один раз; ответ ассистента создаётся и дополняется по мере SSE-событий. Реализуй `AbortController`, кнопку Stop и клавишу Esc, защиту от двойной отправки, пустого текста и поздних чанков после отмены. История остаётся в памяти страницы. Разбор SSE вынеси в понятную небольшую функцию; учти, что сетевой чанк не совпадает с границей события. Запусти сценарии на макете T03».

**Артефакты:** клиентская логика и тесты парсера/переходов состояния при наличии выделенных функций. **Приёмка:** три порции текста видны до завершения; Stop быстро переводит UI в состояние «остановлено» и прерывает поток; новый запрос после Stop работает; история отправляется в пределах лимитов DESIGN.md, включая непустой частичный ответ без служебной метки; 429/обрыв показывают ошибку без потери уже полученного текста; запасной клиентский таймер не оставляет зависший UI. Код не должен содержать ложных задержек ради демонстрации потока.

### Q07 — сценарная и визуальная проверка

**Передать агенту:** «Проверь приложение по матрице ниже в браузере на десктопе и мобильной ширине. Исправь найденные дефекты, сохрани доказательства и результаты в `docs/QA.md`. Повтори только затронутые проверки. Удели внимание Enter/Shift+Enter, порядку Tab, видимому фокусу, `aria-live`, длинному тексту, скроллу и Stop на медленном потоке. Не меняй дизайн без записи причины».

**Минимальная матрица:** пустая отправка; обычный поток; повторное сообщение с историей; Stop и Esc до первого чанка и после первого; следующее сообщение после частичного ответа; HTTP 429; таймаут; сеть недоступна; разрыв в середине; длинный ответ и следующий запрос после него; диалог длиннее 20 сообщений или 20 000 символов; 390 px; клавиатура без мыши, включая Enter/Shift+Enter; обновление страницы (история сбрасывается согласно принятому решению). **Приёмка:** `docs/QA.md` содержит фактический результат каждого пункта, окружение/команду и ссылки на изображения; критические дефекты исправлены; lint/build/test проходят. Не писать «проверено» по одному скриншоту.

### R08 — документация и ревизия

**Передать агенту:** «Приведи README к виду, с которым проверяющий сможет за 5 минут запустить проект: требования, установка, `.env.local`, выбор бесплатной модели, запуск, тесты, ключевые решения и почему они приняты, сознательное несогласие с требованием про удаление браузерного outline, ограничения и что сделать при наличии ещё одного дня. Перенеси краткий честный ИИ-лог из `WORKLOG.md` в README, включая реальные ошибки агента и исправления, если они были. Добавь лицензию по условию задания. Просмотри diff на секреты, лишние зависимости и сложность кода; исправь найденное. Финально запусти lint, test, build и `git diff --check`».

**Артефакты:** README, LICENSE, обновлённые логи/документы. **Приёмка:** инструкции выполняются с чистой копии репозитория; реальные проверки указаны; нет ключа/личных данных; известные ограничения названы; история коммитов объясняет этапы. Ссылку на сайт добавит P09, если её ещё нет.

### P09 — GitHub, PR, публикация

**Передать агенту:** «Проверь готовность по `TASK.md`, создай или подключи публичный GitHub-репозиторий, отправь рабочую ветку, оформи PR с кратким описанием и результатами проверок. После ревью слей PR в `main`. Проверь локальный живой сценарий с реальной моделью и запуск по README. Если остаётся время и доступен подходящий аккаунт, опубликуй проект на Vercel: секрет `OPENROUTER_API_KEY` задай в настройках проекта, проверь production-сборку и живой сценарий потока/Stop на URL. Обнови README ссылками, передай URL репозитория, PR и, если есть, сайта. Не помещай ключ в команды, логи или файлы». Если аккаунт или ключ потребуют действия владельца, подготовь всё остальное и чётко назови необходимую операцию.

**Артефакты:** GitHub URL, слитый PR URL, запись проверки в `docs/QA.md`, финальный `WORKLOG.md`; production URL, если деплой выполнен. **Приёмка:** репозиторий публичен; PR содержит описание и проверки и слит в `main`; локально идёт реальный потоковый ответ, Stop и Esc работают; на мобильном UI пригоден; в браузере и публичном Git нет секрета. Если сайт опубликован, он открывается без ошибок и проверен на реальной модели. Решение о Vercel основано на текущей архитектуре Next.js; смену хостинга оформить как отдельное решение с причиной. Ссылку на GitHub кандидату останется отправить в исходную переписку с работодателем.

## 5. Решения и зависимости

| Вопрос | Рабочее решение | Когда подтвердить / что блокирует |
| --- | --- | --- |
| Стек | Next.js App Router + TypeScript, один серверный route handler | S02; изменить только при конкретном техническом препятствии |
| Модель | Бесплатная модель OpenRouter с поддержкой streaming | A05 проверяет актуальный ID и ограничения по официальной документации |
| Ключ | `OPENROUTER_API_KEY` только в server env | Для макета не нужен; нужен владельцу до живого теста и P09 |
| История | Только в памяти страницы, без БД | C06; сброс при refresh ожидаем |
| Протокол | SSE от OpenRouter через серверный маршрут | A05/C06; тестировать границы событий и отмену |
| Дизайн-навык | Рекомендация в `DESIGN_SKILLS.md`; проект не зависит от его установки | D01 может применять, если доступен; отсутствие не блокирует задачу |
| Тесты | Локальный макет upstream + небольшие автоматические проверки + ручной браузерный сценарий | T03 задаёт основу; A05/C06/Q07 наполняют проверки |
| Хостинг | Vercel для Next.js и серверного ключа, если решено публиковать сайт | P09 проверяет лимиты/актуальные условия перед необязательным деплоем |
| Git | Отдельный репозиторий; `codex/chat-app` — документальная база, D01–P09 — ветки этапов | Локальные ветки созданы; remote появится в P09 |

**Открытые зависимости перед сдачей:** аккаунт GitHub с правом создать/подключить репозиторий; рабочий OpenRouter API key; доступная бесплатная streaming-модель на момент живого теста. Доступ к Vercel нужен только для необязательного сайта. Эти зависимости не мешают D01–Q07 благодаря локальному макету.

## 6. Финальный критерий готовности

- Все обязательные пункты `TASK.md` подтверждены в `docs/QA.md` или в README.
- `npm run lint`, `npm test`, `npm run build` проходят из чистой установки.
- Есть публичный GitHub-репозиторий; PR и AI-log показывают последовательность работы. Публичный URL сайта добавлен, если выполнен деплой.
- Ни в Git, ни в клиентском коде, ни в браузерных ответах нет API-ключа.
- Задача воспроизводима по README, а код остаётся понятным джуну без отдельной устной инструкции.
