# Design Document: одностраничный чат с ИИ

Статус: проектирование, 24 сентября 2026. Источник требований — [TASK.md](./TASK.md). Этот документ фиксирует план, а не утверждает, что приложение уже готово. Если реализация изменит решение, обновить документ и объяснить причину в README.

## 1. Цель и границы

Сделать небольшой чат на React: пользователь отправляет сообщение, видит ответ бесплатной модели OpenRouter по мере появления текста и может остановить генерацию. Результат должен работать на телефоне и с клавиатуры. Проверяющий должен суметь запустить проект локально, посмотреть Network, историю Git, PR и объяснения решений. Публичный сайт полезен для демонстрации, но бриф требует публичный GitHub-репозиторий, а не обязательный деплой.

**В первой версии:** один диалог, одна зафиксированная бесплатная модель, текстовые сообщения, стриминг, отмена, обработка ошибок, история до обновления страницы, адаптивная и доступная форма.

**За пределами первой версии:** аккаунты, база данных, несколько чатов, загрузка файлов, выбор модели пользователем, Markdown, тёмная тема, автоповтор запросов. Это не обязательные требования. Если останется время, Markdown может стать отдельным маленьким PR после основной работоспособности.

Ориентир времени из брифа — 2–6 часов чистой работы. Приоритет: рабочий диалог → стриминг/остановка/ошибки → доступность и мобильный экран → процесс/документы → бонусы.

## 3. Основные решения

| Вопрос | Решение | Причина и компромисс |
| --- | --- | --- |
| Фронт и сервер | Next.js App Router + React + TypeScript, один клиентский компонент чата и один `POST` Route Handler. | Одна кодовая база, один `npm run dev`, один деплой. Нужно понять только границу `use client` и серверный маршрут. |
| Хостинг при необязательном деплое | Vercel, подключённый к отдельному GitHub-репозиторию. | Поддерживаются Next.js Route Handlers, потоковые ответы, секреты и preview на PR. До публикации проверить допустимость своего тарифа; см. §10. |
| Модель | Конкретная доступная модель с `:free`, задаваемая сервером. | Соответствует брифу, предотвращает вызов платной модели через публичный API. Название не вшивать в текст UI до проверки доступности. |
| Передача ответа | OpenRouter SSE → серверный поток → браузерный `fetch` + SSE-парсер. | Сохраняет поступление чанков и минимизирует преобразования на сервере. `EventSource` неудобен для `POST`, поэтому используем `fetch`. |
| Состояние диалога | React state в открытой вкладке. | Нет БД и синхронизации, хватает для требования «в рамках сессии». Reload очищает историю намеренно. |
| Запросы | Одновременно максимум одна генерация. | Нет гонок ответов и неоднозначной кнопки «Стоп». |
| Отмена | Abort на клиенте, сигнал отмены в Vercel Function и в upstream `fetch`. | UI и сервер прекращают работу вместе; остановленный текст сохраняется. Фактическое прекращение вычисления у провайдера зависит от его поддержки. |
| Ошибки | Понятные статусы без автоматического retry. | Повторы могут тратить бесплатную квоту и дублировать ответы. |
| Markdown | Отложен. | Бонус не должен отнимать время у потокового вывода, отмены и доступности. |

## 4. Контракт и поток данных

```text
Браузер → POST /api/chat { messages: [{role, content}, ...] }
        → проверка списка сообщений и лимитов на сервере
        → OpenRouter chat/completions { model: ...:free, stream: true, messages }
        → SSE-байты обратно через /api/chat
        → браузер разбирает события, добавляет delta.content в открытый ответ
```

Сервер принимает только `user`/`assistant` и текстовый `content`; отклоняет пустой ввод, слишком длинное сообщение или историю и неожиданные поля. Практичные стартовые ограничения: до 20 сообщений в запросе, до 4000 символов в сообщении, до 20 000 символов суммарно. UI сохраняет всю историю текущей вкладки, а в запрос отправляет максимально длинный хвост истории, который начинается с сообщения пользователя и одновременно укладывается в оба общих лимита (20 сообщений и 20 000 символов); текущий вопрос всегда включён. Слишком длинный ответ ассистента перед отправкой следующего запроса сокращается в копии для контекста до последних 4000 символов, но полностью остаётся на экране. Если сам вопрос длиннее 4000 символов, UI просит его сократить. Усечение контекста указать в README. Числа можно скорректировать по фактическим тестам. Метод только `POST`, тело только JSON, запрос без нужного формата получает 400/405. Ключ и модель берутся с сервера. Ответы API не кэшировать. Локальный mock из T03 допускается без ключа только при явном серверном переключателе в dev/test; в production этот путь недоступен и отсутствие ключа остаётся ошибкой.

Пока OpenRouter ещё не начал SSE, сервер возвращает JSON-ошибку с понятным кодом и статусом: `429` для лимита, `502` для недоступности модели/провайдера, `500` для отсутствующего ключа (текст без секрета), `400` для неверного ввода. Браузер сначала проверяет HTTP-статус и `Content-Type`, затем читает поток.

После начала SSE HTTP-статус уже нельзя поменять. Поэтому парсер обрабатывает и `data: {"error": ...}` внутри потока; комментарии SSE, пустые события и `[DONE]` не отображает как текст. При обрыве до `[DONE]` показывает состояние прерванного ответа. Байтовые чанки могут разрезать JSON и Unicode-символ; использовать `TextDecoder` в потоковом режиме и корректный SSE-парсер, а не `split('\n')` для каждого `read()`. [Документация OpenRouter по SSE](https://openrouter.ai/docs/api_reference/streaming).

За таймаут upstream отвечает A05: таймер отсутствия данных (ориентир 45 секунд) обновляется при получении байтов, включая служебные SSE-комментарии; отдельный предел полной длительности — ориентир 90 секунд. При срабатывании сервер отменяет upstream и сообщает о таймауте: HTTP-ошибкой до начала ответа, SSE-событием ошибки после начала потока. C06 показывает «Ответ не пришёл вовремя. Попробуйте ещё раз», сохраняет полученный текст и имеет собственный общий таймер с запасом на случай зависания связи браузера с сервером. Значения и `maxDuration` функции подтвердить на реальной бесплатной модели. На Vercel для Node.js функции включить `supportsCancellation` для `/api/chat`, передать `request.signal` в upstream `fetch` и проверить, что Stop действительно разрывает соединение после деплоя. [Документация Vercel по отмене](https://vercel.com/docs/functions/functions-api-reference).

### Состояния одного ответа

`idle → waiting → streaming → complete`. Из `waiting` или `streaming` возможны `stopped`, `rate_limited`, `timeout`, `network_error`, `provider_error`. Все конечные состояния возвращают форму в `idle`. У сообщения ассистента хранить `id`, `content` и локальный статус; служебный статус не отправлять OpenRouter. Пустой ответ ассистента после ошибки/остановки не добавлять в историю; если часть текста пришла, оставить её и показать метку. Следующий запрос передаёт видимые непустые сообщения в пределах лимитов, включая частичный ответ после Stop или ошибки, чтобы контекст модели соответствовал показанному диалогу. Метка «Остановлено» или текст ошибки в `content` не входят.

| Сценарий | Что увидит пользователь | Что происходит с историей |
| --- | --- | --- |
| Успех | Текст нарастает, затем индикатор исчезает. | Полный ответ остаётся. |
| Stop до первого символа | Индикатор исчезает, форма снова активна. | Сообщение пользователя остаётся, пустой ответ не создаётся. |
| Stop после нескольких символов | «Остановлено», форма снова активна. | Полученный фрагмент остаётся. |
| 429 до или во время потока | «Бесплатная модель сейчас перегружена. Попробуйте позже». | Вопрос остаётся; полученный фрагмент при ошибке в SSE сохраняется. |
| Таймаут | «Ответ не пришёл вовремя. Попробуйте ещё раз». | Уже показанный текст остаётся с пометкой. |
| Потеря сети / SSE-ошибка | «Соединение прервалось. Проверьте сеть и попробуйте ещё раз». | Уже показанный текст остаётся с пометкой. |
| Ошибка конфигурации | «Сервис временно недоступен». | Ключ, техническая трассировка и сырой ответ провайдера не показываются. |

Для Stop использовать причину отмены `manual`; для таймера — `timeout`, чтобы не спутать две ситуации. `finally` очищает контроллер, таймеры и флаг генерации. Повторное нажатие Enter, пока идёт запрос, не создаёт второй запрос. Автопрокрутка следует за текстом, только если пользователь уже у нижней границы; ручную прокрутку вверх не сбивать.

## 5. Экран и доступность

- Верхняя строка: короткое название и обозначение выбранной бесплатной модели. Основной экран — история и форма.
- Пустое состояние — содержательное, но короткое. Сразу видны поле и кнопка отправки.
- Сообщения различаются подписью «Вы»/«Ассистент», выравниванием и цветом; смысл не передаётся только цветом.
- `textarea` имеет видимый `label`. Enter отправляет, Shift+Enter добавляет перенос. На мобильной клавиатуре кнопка остаётся полноценным способом отправить сообщение.
- Кнопка «Стоп» появляется/активна только во время генерации; Esc работает при фокусе в чате. После остановки фокус возвращается в поле ввода.
- Индикатор генерации и ошибки доступны скринридеру через подходящий `role=status`/`aria-live`, но каждый токен потока не должен зачитываться отдельно. История — семантический список внутри `main`.
- Стандартный `outline` заменён собственным контрастным `:focus-visible` кольцом для кнопок и поля; Tab показывает его всегда.
- Проверить ширины около 320 и 390 px, десктоп, увеличенный текст, длинные слова/URL, виртуальную клавиатуру и отсутствие горизонтального скролла.

## 6. Безопасность и эксплуатация

Секрет хранится в `.env.local` локально и в server-side переменной окружения Vercel. `.env.local` не коммитить; `.env.example` содержит только имя переменной. Не использовать `NEXT_PUBLIC_` для ключа. Проверять вкладку Network и собранные клиентские файлы на отсутствие ключа. [Документация Next.js по переменным окружения](https://nextjs.org/docs/app/guides/environment-variables).

Публичный `/api/chat` всё равно может быть вызван кем угодно. Защита ключа не является защитой квоты. Минимальные меры для демо: одна серверная модель `:free`, лимиты длины/истории, отсутствие автоматических повторов, ограничение ключа в OpenRouter, если доступно в аккаунте, и наблюдение за расходом квоты. При заметном злоупотреблении — ограничение частоты запросов на стороне платформы. Не обещать абсолютную защиту без аккаунтов и выделенного rate limiter.

Провайдер бесплатной модели может хранить запросы по собственной политике. Не отправлять в демо настоящие личные данные; это кратко указать рядом с полем или в README. Не логировать тексты сообщений и заголовок Authorization. Тексты ответов выводить как текст React; при добавлении Markdown позднее применять безопасный рендер без произвольного HTML.

## 7. Проверка готовности

Автоматические проверки: `npm run lint`, `npm run build`, небольшой набор тестов для разбора SSE/переходов состояний, если логика выделена из компонента. Тесты должны проверять реальные края: событие SSE, разрезанное между байтовыми чанками; 429 до стрима; ошибка внутри стрима; Stop после части текста; отсутствие `[DONE]`. Не писать тесты, повторяющие только JSX.

Ручной smoke test локально; на preview URL повторить основные сценарии, если выполнен деплой:

1. Отправить вопрос, увидеть несколько приращений текста до окончания запроса.
2. Остановить ответ до первого чанка и после нескольких чанков; фрагмент остаётся, следующий вопрос отправляется.
3. Смоделировать 429, таймаут и обрыв сети; в каждом случае индикатор исчезает и форму можно использовать.
4. Отправить второй вопрос, ссылающийся на первый ответ; убедиться, что контекст передаётся.
5. Tab по всем контролам, Enter, Shift+Enter, Esc; проверить видимый фокус и сообщения скринридера.
6. Проверить мобильную ширину и длинный текст. В Network запросы идут к собственному `/api/chat`, а ключ нигде не виден.
7. Обновить страницу: история исчезает, как описано в README.

Для ошибок лучше использовать управляемый mock OpenRouter в тесте/локальной среде, чтобы не расходовать бесплатную квоту. Реальный запрос нужен для финальной проверки интеграции и потока.

## 8. Пушбек к брифу

**Строки 40–42 и 52–53 конфликтуют, если понимать второе пожелание буквально.** Удаление видимого фокуса делает Tab-навигацию непрозрачной. Поэтому убрать только *стандартную* браузерную обводку и сделать свою, заметную для `:focus-visible`. В README написать это прямо. Результат соответствует визуальному пожеланию и сохраняет доступность.

**Бесплатная модель не гарантирует стабильный ответ.** Бриф отдельно требует обработать 429/таймаут/обрыв. Поэтому демо показывает честный сбой, сохраняет уже пришедший текст и не делает автоматических повторов. Не подменять бесплатную модель платной без объяснения.

## 11. Выбор хостинга: Sites или Vercel

**Рекомендация для необязательного деплоя: Vercel.** Для этого тестового важно показать именно собственный публичный GitHub-репозиторий с ветками и PR, а также простой серверный маршрут с секретом, поток и отмену. Vercel напрямую связывает GitHub push/PR с preview и merge в `main` с production; поддерживает потоковые функции и передачу сигнала отмены клиентского запроса в Node.js Function. [Git-интеграция](https://vercel.com/docs/git), [стриминг](https://vercel.com/docs/functions/streaming-functions), [отмена](https://vercel.com/docs/functions/functions-api-reference).

**Sites технически подходит для сайта с серверным Worker, секретом и публичным доступом**, согласно доступному в этом рабочем окружении workflow Sites. Но новый Site сначала создаётся приватным и публикуется через собственный процесс версий/развёртывания. Для данного задания это добавляет отдельный путь доставки поверх обязательного GitHub PR. Если впоследствии понадобится быстрое демонстрационное размещение, Sites можно рассмотреть, но не стоит делать его основным источником правды для сдачи этого задания.

Стоимость/условия Vercel нужно проверить для собственного аккаунта: [Hobby ограничен личным некоммерческим использованием](https://vercel.com/docs/plans/hobby). Тестовый проект кандидата может требовать отдельной оценки условий использования; этот документ не обещает, что любой бесплатный тариф подходит. Длительность функции также зависит от текущей конфигурации; задать явный предел и проверить фактическое поведение, а не полагаться на значения по умолчанию. [Лимиты длительности](https://vercel.com/docs/functions/configuring-functions/duration).
