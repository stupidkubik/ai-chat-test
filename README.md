# Диалог — чат с ИИ

Одностраничный чат на Next.js 16, React 19 и TypeScript. Ответ бесплатной модели OpenRouter появляется по мере генерации. Можно остановить ответ кнопкой «Стоп» или клавишей Esc; уже полученный текст остаётся в истории. [Открыть чат](https://ai-chat-test-lake.vercel.app/) · [Публичный репозиторий](https://github.com/stupidkubik/ai-chat-test) · [Исходный бриф](TASK.md) · [История этапов и PR](docs/PROGRESS.md).

## Запуск за пять минут

Нужны Node.js **20.9+**, npm и собственный [ключ OpenRouter](https://openrouter.ai/settings/keys). Версия, использованная при разработке, указана в `.nvmrc` (24.18.0); `nvm` удобен, но не обязателен.

```bash
# Выполнить в корне репозитория; при использовании nvm сначала: nvm use
npm ci
cp .env.example .env.local
```

Откройте `.env.local` и вставьте ключ в значение `OPENROUTER_API_KEY=`. Затем:

```bash
npm run dev
```

Откройте <http://localhost:3000>. Если ключ добавлен после запуска сервера, перезапустите `npm run dev`. Файл `.env.local` исключён из Git. Не помещайте ключ в переменные `NEXT_PUBLIC_*` и не отправляйте его через браузер.

Модель фиксирована на сервере как `openrouter/free`: OpenRouter выбирает доступную бесплатную модель для каждого запроса. Поэтому отдельный выбор модели в интерфейсе не нужен, а доступность и скорость конкретного исполнителя могут меняться. Если бесплатная модель перегружена, приложение показывает ошибку 429 и позволяет повторить запрос позднее.

**Проверки без ключа:** `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`. Тесты используют локальный mock и не обращаются к OpenRouter. Для ручной проверки UI без ключа есть [инструкция по mock](docs/TESTING.md): он запускается в отдельном терминале и включается только серверной переменной в режиме разработки.

## Как это устроено

- Браузер отправляет сообщения только в `POST /api/chat`. Сервер проверяет роли, размер истории и текста, добавляет секретный заголовок и обращается к OpenRouter. Модель и адрес провайдера браузер выбрать не может.
- OpenRouter отдаёт SSE. Сервер передаёт поток дальше, а клиент собирает события и дописывает ответ по фрагментам. Кнопка «Стоп» и Esc отменяют браузерный запрос; на сервере сигнал закрытия передаётся в запрос к провайдеру. Частичный ответ остаётся видимым и участвует в следующем вопросе.
- Для 429, таймаута, ошибки провайдера и сетевого обрыва показаны понятные состояния. После ошибки форма снова активна. Автоматических повторов нет: они могли бы незаметно повторять сообщения и тратить бесплатную квоту.
- Диалог хранится в памяти вкладки и сбрасывается при обновлении. Это осознанный выбор для небольшого тестового задания: нет постоянного хранения текста на устройстве или сервере. При отправке длинной истории клиент выбирает её хвост: до 20 сообщений, 4000 символов на сообщение и 20 000 символов суммарно. На экране предыдущие ответы остаются целиком.
- Next.js выбран ради одного приложения с серверным маршрутом и простого запуска. Отдельный API-сервер и база данных здесь не нужны. Подробнее: [технические решения](DESIGN.md), [проверка сценариев](docs/QA.md).

## Решение по фокусу

В брифе одновременно требуются полноценная клавиатурная навигация и удаление браузерной обводки у элементов. Полное удаление видимого фокуса сделало бы Tab-навигацию непонятной. Поэтому стандартный вид заменён собственным контрастным `:focus-visible` кольцом для поля, кнопок и прокручиваемой истории. Enter отправляет, Shift+Enter добавляет строку, Esc останавливает ответ.

## Проверенный объём и ограничения

В [Q07 и P09](docs/QA.md) проверены живой поток, история, Stop, Esc, мобильная ширина и клавиатура; в P09 основной адрес открылся в браузере без авторизации. Ошибки 429, таймаут и обрывы проверены локальным mock. Автоматические тесты покрывают серверный маршрут, SSE-парсер, контекст и mock. Проверки на физическом телефоне и конкретном скринридере не проводились. Фактическое прекращение вычисления у OpenRouter после отмены нельзя подтвердить со стороны приложения.

Отдельный Preview deployment, созданный для Q07, не имел ключа и возвращал ошибку конфигурации при отправке сообщения. На Q07 Production требовал Vercel Login; при повторной проверке P09 [основной адрес](https://ai-chat-test-lake.vercel.app/) открылся без авторизации, а реальный поток завершился. Условия аккаунта и стабильность внешнего доступа следует проверить перед передачей работодателю. [История деплоя](docs/DEPLOYMENT.md) записана отдельно.

Markdown и тёмная тема оставлены как необязательные улучшения. Текст модели отображается обычным текстом. Пожелание уложиться в 2–6 часов чистой работы не было подтверждено замером: [WORKLOG.md](WORKLOG.md) фиксирует выполненные этапы и проверки, но не точное активное время. Выдавать оценку времени за измеренный факт было бы неверно.

Если бы был ещё день, я бы проверил экран с виртуальной клавиатурой на физических телефонах, провёл проход со скринридером, настроил отдельный работающий Preview и проверил стабильность публичного адреса. Затем добавил бы сохранение истории по выбору пользователя и Markdown с безопасным рендерингом.

## Как использовался ИИ

Codex помогал разбирать бриф, проектировать интерфейс, писать код, тесты и документацию, проводить ревью и браузерную проверку. Решения и результаты по этапам записаны в [WORKLOG.md](WORKLOG.md); завершённые этапы проходили через отдельные ветки и PR.

ИИ ошибался и в реализации, и в проверке. В раннем UI прокручиваемая история получила `tabIndex={-1}`: проверка на коротком экране и замечание в PR показали, что пользователь клавиатуры не может перейти к ней и прокрутить старые сообщения. Истории вернули `tabIndex={0}` и видимый фокус. Позже ревью потокового клиента выявило, что пустые старые ходы попадали в контекст следующего запроса, а статус частичного ответа исчезал после нового сообщения. Это исправлено в [дополнительном PR #7](https://github.com/stupidkubik/ai-chat-test/pull/7) с тестами. При проверке деплоя ИИ сначала принял переданный URL за Production; `vercel inspect` показал, что это Preview без ключа. Результаты сред разделены в [Q07](docs/QA.md).
