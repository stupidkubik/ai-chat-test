# Диалог — чат с ИИ

Одностраничный чат на Next.js 16, React 19 и TypeScript. Ответ бесплатной модели OpenRouter появляется по мере генерации, его можно остановить кнопкой «Стоп» или клавишей Esc. [Открыть чат](https://ai-chat-test-lake.vercel.app/) · [Бриф](TASK.md) · [История PR](https://github.com/stupidkubik/ai-chat-test/pulls?q=is%3Apr)

## Запуск

Нужны Node.js 20.9+ и [ключ OpenRouter](https://openrouter.ai/settings/keys).

```bash
npm ci
cp .env.example .env.local   # вставьте ключ в OPENROUTER_API_KEY=
npm run dev                  # http://localhost:3000
```

Без ключа работают `npm test`, `npm run lint`, `npm run typecheck` и `npm run build`: тесты идут на локальном mock OpenRouter. Для ручной проверки интерфейса без ключа есть [инструкция по mock](docs/TESTING.md), в ней сценарии 429, обрывов, таймаута и markdown.

## Ключевые решения

- **Ключ только на сервере.** Браузер ходит в `POST /api/chat`. Сервер проверяет сообщения, сам выбирает модель и адрес провайдера и добавляет ключ. Во вкладке Network ключа нет.
- **Модель `openrouter/free`.** OpenRouter выбирает доступную бесплатную модель на каждый запрос, поэтому выбор модели в интерфейсе не нужен. Цена этого решения: скорость и стиль ответа меняются от запроса к запросу.
- **Сервер разбирает SSE, а не проксирует поток как есть.** Так он превращает ошибки провайдера внутри потока в безопасные коды, не отдаёт браузеру сырой текст ошибки и замечает обрыв до `[DONE]`.
- **Стоп сохраняет частичный ответ.** Отмена доходит от кнопки через `AbortController` и `request.signal` до запроса к OpenRouter. Частичный ответ остаётся на экране и уходит в контекст следующего вопроса.
- **Без автоповторов.** Они незаметно тратят бесплатную квоту и могут отправить сообщение дважды. После ошибки есть кнопка «Повторить»: она отправляет тот же вопрос с тем же контекстом.
- **История живёт до перезагрузки.** Текст разговора не хранится ни на устройстве, ни на сервере. Для тестового задания это самый простой и безопасный вариант. В следующий вопрос уходит хвост истории: до 20 сообщений и 20 000 символов.
- **Таймауты считаются по бездействию.** Сервер обрывает запрос после 45 с тишины от провайдера и ждёт первые данные модели не дольше 90 с: одни служебные keepalive-сообщения этот срок не продлевают. Когда ответ пошёл, общего срока нет: длинный живой ответ ограничен только `maxDuration` функции на Vercel (300 с).

## Пушбек по брифу: outline и клавиатура

Бриф требует и полноценную клавиатурную навигацию, и удаление браузерной обводки у элементов. Это противоречие: без видимого фокуса пользователь клавиатуры не видит, где находится. Поэтому я не убрал обводку, а заменил стандартную на собственное контрастное кольцо `:focus-visible`. Оно есть у поля, кнопок, примеров запросов и прокручиваемой истории. Enter отправляет, Shift+Enter переносит строку, Esc останавливает ответ.

## Защита прокси

Открытый `/api/chat` позволил бы любому расходовать ключ через curl. Поэтому сделаны две защиты:

- Запросы с чужого сайта и без признаков своей страницы (`Sec-Fetch-Site: same-origin` или совпадающий `Origin`) получают 403. Это не спасает от человека, который подделает заголовок в curl, но закрывает использование прокси с чужих страниц.
- Лимит 10 запросов в минуту на IP, превышение даёт 429 с понятным текстом. Счётчик живёт в памяти одного экземпляра функции: на Vercel у разных экземпляров свои счётчики, и они обнуляются при холодном старте. Настоящий лимит нужно хранить во внешнем хранилище, например Upstash Redis.

## Проверено и ограничения

Автотесты покрывают серверный маршрут, SSE-парсер, клиентский поток, сборку контекста и mock. На живом деплое проверены поток, Стоп, Esc, клавиатура и ширина 390 px ([QA](docs/QA.md)). Ошибки 429, таймаут и обрывы проверены на mock.

Не проверялось: физические телефоны с экранной клавиатурой и работа со скринридером. Со стороны приложения нельзя подтвердить, что OpenRouter действительно прекращает генерацию после отмены.

## Что бы я сделал дальше

- Лимит запросов во внешнем хранилище вместо памяти функции.
- Проход со скринридером и проверку на телефонах.
- Сохранение истории по выбору пользователя, например в `sessionStorage` с кнопкой «Очистить».
- E2E-тест в Playwright на mock: отправка → поток → Esc → повторная отправка. Сейчас этот сценарий проверен вручную.

## Как я работал с ИИ

Первоначально я взял бриф и вытащил из него всю задачу. На основе данных я составил общую концепцию проекта. На основе концепции написал подробный план разработки, который разбил на логичные этапы. Сделал прототип дизайна, по частям написал приложение и задеплоил его.

Codex вёл этапы D01–P09 по плану и открывал PR, бот Codex Review комментировал PR, я принимал этапы и сливал PR. Полировку перед сдачей я делал с Claude Code.

Изначально деплой в плане был указан в самом конце разработки. Но я сделал продакшн-деплой перед этапом тестирования, чтобы все проверить на реальной работе приложения.

После финальной проверки Codex я решил сделать дополнительный проход Claude, чтобы получить второе мнение о качестве проекта. Поправил несколько слабых мест и добавил бонусные части задания.
